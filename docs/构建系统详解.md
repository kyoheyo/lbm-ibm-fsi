## 1 整体构建流程概览

本项目使用 **Cargo（Rust 构建工具）驱动 CMake（C++ 构建系统）** 的混合构建方案。
完整的 `cargo build` 执行顺序如下：

```
cargo build
    │
    ├─① 检测 build.rs 是否需要重新执行
    │      (根据 cargo:rerun-if-changed 记录的路径/环境变量哈希)
    │
    ├─② 执行 bindings/build.rs
    │      │
    │      ├─ cmake configure（读取 CMakeLists.txt，生成 Makefile/build.ninja）
    │      │       └─ 顶层 CMakeLists.txt
    │      │               ├─ 全局 C++ 标准、编译器标志、MSVC 运行时设置
    │      │               ├─ 查找 MPI / OpenMP / CUDA
    │      │               ├─ add_subdirectory(core)         → core/CMakeLists.txt
    │      │               └─ add_subdirectory(core/tests)   → 仅 BUILD_TESTS=ON 时
    │      │
    │      ├─ cmake --build（编译所有 .cpp，生成 liblbm_core.a）
    │      │       └─ 产物路径：<cargo_out>/lib/liblbm_core.a
    │      │
    │      └─ 打印 cargo: 指令（link-search / link-lib / rerun-if-changed）
    │
    └─③ 编译 bindings/src/lib.rs，链接 liblbm_core.a
            └─ 产物：target/{debug|release}/liblbm_bindings.rlib
```

## 2 bindings/build.rs — 逐步解析

文件位置：`bindings/build.rs`

Cargo 的**构建脚本（build script）**机制：在编译 crate 之前，Cargo 会先编译并运行 crate 根目录下的 `build.rs`。该脚本通过向标准输出打印 `cargo:` 开头的特殊指令与 Cargo 通信。

### 2.1 cargo: 协议指令速查表

| 指令 | 作用 |
|------|------|
| `cargo:rustc-link-search=native=<路径>` | 告诉 rustc 在该目录搜索 `.a` / `.lib` 文件 |
| `cargo:rustc-link-lib=static=<名称>` | 静态链接 `lib<名称>.a`（Unix）/ `<名称>.lib`（Windows） |
| `cargo:rustc-link-lib=<名称>` | 动态链接系统库 |
| `cargo:rerun-if-changed=<路径>` | 指定路径变化时重新运行本脚本 |
| `cargo:rerun-if-env-changed=<变量>` | 指定环境变量变化时重新运行本脚本 |

### 2.2 第一步：确定项目根目录

```rust
let manifest_dir = PathBuf::from(env!("CARGO_MANIFEST_DIR"));
let repo_root = manifest_dir.parent().unwrap();
```

**`CARGO_MANIFEST_DIR`** 是 Cargo 为每个 crate 自动注入的环境变量，值为该 crate 的 `Cargo.toml` 所在目录的**绝对路径**。

对本项目而言：
- `manifest_dir` = `/…/lbm-ibm-fsi/bindings/`
- `repo_root`    = `/…/lbm-ibm-fsi/`（含顶层 `CMakeLists.txt`）

使用绝对路径而非相对路径，是因为 `build.rs` 由 Cargo 在任意工作目录下运行，不能假设当前目录。

### 2.3 第二步：推断 cmake 构建类型

```rust
let cmake_build_type = if std::env::var("OPT_LEVEL").unwrap_or_default() == "0" {
    "Debug"
} else {
    "Release"
};
```

**`OPT_LEVEL`** 是 Cargo 注入的环境变量，反映当前编译配置的优化级别：
- `cargo build`           → `OPT_LEVEL=0` → cmake `Debug`
- `cargo build --release` → `OPT_LEVEL=3` → cmake `Release`

此值稍后会传给 cmake 的 `CMAKE_BUILD_TYPE`（影响单配置生成器如 Ninja），并由 cmake-rs crate 用于决定多配置生成器（Visual Studio）的 `--config` 参数。

> **为什么要对齐？**  
> MSVC 的 Debug / Release 配置使用不同的运行时库（`/MDd` vs `/MD`）。
> 若不对齐，Rust 用 `/MD` 而 C++ 库用 `/MDd`，链接时会出现 LNK1120 错误。
> 详见 [§7 常见构建错误](#7-常见构建错误与解决方案)。

### 2.4 第三步：调用 cmake::Config 构建 C++ 库

```rust
let dst = cmake::Config::new(repo_root)
    .define("BUILD_TESTS", "OFF")
    .define("ENABLE_MPI",    std::env::var("LBM_ENABLE_MPI")
                             .unwrap_or_else(|_| "OFF".into()))
    .define("ENABLE_OPENMP", std::env::var("LBM_ENABLE_OPENMP")
                             .unwrap_or_else(|_| "OFF".into()))
    .define("CMAKE_BUILD_TYPE", cmake_build_type)
    .build();
```

`cmake::Config` 是 [`cmake` crate](https://crates.io/crates/cmake) 提供的构建器 API，`.build()` 内部依次执行：

```
1. cmake <repo_root>
       -DBUILD_TESTS=OFF
       -DENABLE_MPI=OFF
       -DENABLE_OPENMP=OFF
       -DCMAKE_BUILD_TYPE=Debug|Release
       -B <out_dir>/build
       （out_dir = Cargo 管理的临时目录，位于 target/*/build/lbm-bindings-*/out/）

2. cmake --build <out_dir>/build
       （等价于 make / ninja，编译所有 C++ 源文件）

3. cmake --install <out_dir>/build --prefix <out_dir>
       （将 liblbm_core.a 安装到 <out_dir>/lib/）
```

返回值 `dst` = `<out_dir>`，后续步骤用 `dst.display()` 拼接路径。

**各 `.define()` 的含义：**

| 键 | 值 | 说明 |
|---|---|---|
| `BUILD_TESTS` | `OFF` | 不编译 C++ 测试可执行文件，加速构建 |
| `ENABLE_MPI` | 默认 `OFF`，可通过 `LBM_ENABLE_MPI=ON` 覆盖 | 在无 MPI 的 CI / 开发机上安全构建 |
| `ENABLE_OPENMP` | 默认 `OFF`，可通过 `LBM_ENABLE_OPENMP=ON` 覆盖 | 同上 |
| `CMAKE_BUILD_TYPE` | `Debug` 或 `Release` | 与 Cargo 配置对齐，防止 MSVC 运行时库冲突 |

> **注意**：直接执行 `cmake` 时，`CMakeLists.txt` 中 MPI/OpenMP 的默认值是 `ON`。
> 两种构建路径的默认值不同，详见 [§6 对比表](#6-cargo-build-与独立-cmake-的行为差异对比)。

### 2.5 第四步：指定链接器搜索路径

```rust
println!("cargo:rustc-link-search=native={}/lib", dst.display());
```

cmake install 完成后，静态库位于：
- Unix：`<dst>/lib/liblbm_core.a`
- Windows：`<dst>/lib/lbm_core.lib`

此指令告诉 rustc 在该目录中搜索 `.a` / `.lib` 文件。

### 2.6 第五步：声明静态链接 C++ 核心库

```rust
println!("cargo:rustc-link-lib=static=lbm_core");
```

`static=` 前缀表示静态链接，rustc 会在 `link-search` 目录中查找：
- Unix：`liblbm_core.a`（`lib` 前缀由 rustc 自动补全）
- Windows：`lbm_core.lib`

### 2.7 第六步：链接 C++ 标准库（平台相关）

```rust
let target_os = std::env::var("CARGO_CFG_TARGET_OS").unwrap_or_default();
match target_os.as_str() {
    "macos" | "ios" => println!("cargo:rustc-link-lib=c++"),
    "windows"       => {}
    _               => println!("cargo:rustc-link-lib=stdc++"),
}
```

C++ 代码使用了标准库（`std::vector` 等），必须链接对应的 C++ 运行时：

| 平台 | C++ 运行时库 | 为什么 |
|------|------------|--------|
| macOS / iOS | `libc++`（Apple LLVM 默认） | GCC `libstdc++` 在 macOS 上已弃用 |
| Linux / FreeBSD 等 | `libstdc++`（GCC 运行时） | 绝大多数 Linux 发行版的默认 C++ 运行时 |
| Windows（MSVC） | 自动链接，无需声明 | MSVC 工具链内置 `msvcrt.lib` 等，显式声明 `stdc++` 反而报错 |

使用 `CARGO_CFG_TARGET_OS`（而非 `#[cfg(target_os)]`）的原因：build.rs 是**宿主机**代码，而 `CARGO_CFG_TARGET_OS` 反映的是**目标平台**，在交叉编译场景下两者可能不同。

### 2.8 第七步：增量构建守卫

```rust
println!("cargo:rerun-if-changed=../core/src");
println!("cargo:rerun-if-changed=../core/include");
println!("cargo:rerun-if-env-changed=LBM_ENABLE_MPI");
println!("cargo:rerun-if-env-changed=LBM_ENABLE_OPENMP");
```

这四条指令告诉 Cargo：**只有**以下情况才需要重新运行 build.rs（进而重新触发 cmake）：
- `core/src/` 下有文件被修改（C++ 源文件）
- `core/include/` 下有文件被修改（C++ 头文件）
- 环境变量 `LBM_ENABLE_MPI` 发生变化
- 环境变量 `LBM_ENABLE_OPENMP` 发生变化

其他情况（如修改 Rust 源文件）不触发 cmake，极大缩短增量编译时间。  
详见 [§8 增量构建机制详解](#8-增量构建机制详解)。

## 3 CMakeLists.txt（顶层）— 逐行解析

文件位置：`CMakeLists.txt`

顶层 CMakeLists.txt 是 CMake 的入口文件，负责全局配置并将工作委派给子目录。

### 3.1 CMake 版本要求

```cmake
cmake_minimum_required(VERSION 3.20)
```

要求 CMake 3.20 或更高版本。3.20 起支持：
- `CMAKE_MSVC_RUNTIME_LIBRARY`（强制 MSVC 运行时库，解决 LNK1120）
- `target_*` 命令的完善属性传播
- 更稳定的 `FetchContent` 模块

低于此版本的 CMake 处理本文件时会立即报错并退出。

### 3.2 项目声明

```cmake
project(lbm_ibm_fsi VERSION 0.1.0 LANGUAGES CXX)
```

- `lbm_ibm_fsi`：CMake 内的项目名称（不影响生成的库文件名）
- `VERSION 0.1.0`：定义 `PROJECT_VERSION` 等变量，供后续查询
- `LANGUAGES CXX`：只启用 C++ 语言；CUDA 在需要时通过 `enable_language(CUDA)` 单独启用

### 3.3 C++ 语言标准配置

```cmake
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

| 变量 | 含义 |
|------|------|
| `CMAKE_CXX_STANDARD 17` | 要求 C++17（用到结构化绑定、`if constexpr`、`std::optional` 等） |
| `CMAKE_CXX_STANDARD_REQUIRED ON` | 若编译器不支持 C++17，立即报错而不是降级 |
| `CMAKE_CXX_EXTENSIONS OFF` | 禁用 GNU/MSVC 专有扩展（如 `__int128`），保持跨平台可移植性 |

这三个变量会自动传播到 `add_subdirectory()` 引入的所有目标，无需在子目录中重复声明。

### 3.4 编译开关（option）

```cmake
option(ENABLE_MPI    "Enable MPI parallelism"   ON)
option(ENABLE_OPENMP "Enable OpenMP parallelism" ON)
option(ENABLE_CUDA   "Enable CUDA GPU backend"   OFF)
option(BUILD_TESTS   "Build unit tests"          ON)
```

`option(名称 "描述" 默认值)` 定义可在命令行通过 `-D名称=ON/OFF` 覆盖的布尔变量。

**默认值与 cargo build 覆盖值对比**（详见 [§6](#6-cargo-build-与独立-cmake-的行为差异对比)）：

| 开关 | cmake 默认 | cargo build 传入值 |
|------|-----------|-------------------|
| `ENABLE_MPI` | `ON` | `OFF`（可用 `LBM_ENABLE_MPI=ON` 覆盖） |
| `ENABLE_OPENMP` | `ON` | `OFF`（可用 `LBM_ENABLE_OPENMP=ON` 覆盖） |
| `ENABLE_CUDA` | `OFF` | `OFF`（未覆盖） |
| `BUILD_TESTS` | `ON` | `OFF`（固定关闭） |

### 3.5 编译器优化与警告选项

```cmake
if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
    add_compile_options(-O3 -march=native -Wall -Wextra)
endif()
```

| 选项 | 作用 |
|------|------|
| `-O3` | 最高优化级别（内联、自动向量化、循环展开等） |
| `-march=native` | 针对当前 CPU 的指令集（AVX2、AVX-512 等）生成最优代码 |
| `-Wall -Wextra` | 开启绝大多数有用的编译警告，尽早暴露潜在问题 |

> **注意**：`-march=native` 生成的二进制文件**不可在其他机器上运行**（可能使用了该机器特有的指令）。在 CI 环境中若需要跨机器分发，应改为 `-march=x86-64` 或删除此选项。

### 3.6 MSVC 专用设置

```cmake
if(MSVC)
    set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreadedDLL")
    add_compile_options(/EHsc)
endif()
```

#### `CMAKE_MSVC_RUNTIME_LIBRARY`

MSVC 提供四种 C++ 运行时库：

| 值 | 编译器开关 | 对应库 | 说明 |
|---|-----------|--------|------|
| `MultiThreadedDLL` | `/MD` | `msvcrt.lib` | Release DLL 运行时（推荐） |
| `MultiThreadedDebugDLL` | `/MDd` | `msvcrtd.lib` | Debug DLL 运行时 |
| `MultiThreaded` | `/MT` | `libcmt.lib` | Release 静态运行时 |
| `MultiThreadedDebug` | `/MTd` | `libcmtd.lib` | Debug 静态运行时 |

**问题根源（LNK1120 / LNK2001）**：

cmake Debug 配置默认使用 `/MDd`（`MultiThreadedDebugDLL`），编译出的 `lbm_core.lib` 会引用 `msvcrtd.dll` 中的调试专有符号（`_calloc_dbg`、`__acrt_iob_func` 等）。  
Rust 链接器（`link.exe`）无论 `cargo build` 还是 `cargo build --release`，始终使用 `/MD`，不携带 `msvcrtd.lib`，因此这些调试符号无法解析 → LNK2001 → LNK1120。

**修复方案**：强制所有 cmake 配置都使用 `/MD`（`MultiThreadedDLL`），确保与 Rust 一致。  
C++ 调试信息（断点、PDB 文件、变量查看）不受影响，因为它们由 `CMAKE_BUILD_TYPE=Debug` 控制，与运行时库选择无关。

#### `/EHsc`

启用标准 C++ 同步异常处理（`/EH` = Exception Handling，`s` = synchronous，`c` = extern "C" 函数不抛异常假设）。

- Visual Studio 生成器会自动添加 `/EHsc`；
- cmake-rs crate 在部分情况下选择 Ninja 生成器，此时不会自动添加；
- 显式设置保证两种生成器行为一致。

### 3.7 MPI 依赖查找

```cmake
if(ENABLE_MPI)
    find_package(MPI REQUIRED)
    message(STATUS "MPI found: ${MPI_CXX_COMPILER}")
endif()
```

`find_package(MPI REQUIRED)` 在系统中查找 MPI 实现（OpenMPI、MPICH、Intel MPI 等）。  
查找成功后，CMake 创建导入目标 `MPI::MPI_CXX`，该目标**自动携带**：
- 编译器参数：`-I<mpi_include_dir>`
- 链接器参数：`-L<mpi_lib_dir> -lmpi -lmpi_cxx`

在 `core/CMakeLists.txt` 中通过 `target_link_libraries(lbm_core PUBLIC MPI::MPI_CXX)` 传递这些参数，无需手动填写。

### 3.8 OpenMP 依赖查找

```cmake
if(ENABLE_OPENMP)
    find_package(OpenMP REQUIRED)
    message(STATUS "OpenMP found: version ${OpenMP_CXX_VERSION}")
endif()
```

类似 MPI，查找成功后创建导入目标 `OpenMP::OpenMP_CXX`，自动携带 `-fopenmp`（GCC/Clang）或 `/openmp`（MSVC）等编译/链接标志。

### 3.9 子目录

```cmake
add_subdirectory(core)

if(BUILD_TESTS)
    enable_testing()
    add_subdirectory(core/tests)
endif()
```

- `add_subdirectory(core)` — 进入 `core/CMakeLists.txt`，编译 `liblbm_core.a`（**始终执行**）
- `enable_testing()` — 初始化 CTest 框架，使 `add_test()` 生效
- `add_subdirectory(core/tests)` — 仅 `BUILD_TESTS=ON` 时才进入，编译 `test_lbm` 可执行文件

## 4 core/CMakeLists.txt — 逐行解析

文件位置：`core/CMakeLists.txt`

本文件的职责是：**将 `core/src/` 下所有 C++ 源文件编译并打包为静态库 `liblbm_core.a`**。

### 4.1 源文件列表

```cmake
set(CORE_SOURCES
    src/lbm/lattice.cpp
    src/lbm/solver.cpp
    src/lbm/boundary.cpp
    src/ibm/marker.cpp
    src/ibm/interpolation.cpp
    src/fsi/structure.cpp
    src/fsi/coupling.cpp
    src/capi/lbm_capi.cpp
    src/plugins/plugin_registry.cpp
)
```

按物理模块分组的 `.cpp` 文件列表。每个文件对应的功能：

| 文件 | 模块 | 功能 |
|------|------|------|
| `src/lbm/lattice.cpp` | LBM | D2Q9/D3Q19/D3Q27 格子初始化，宏观量（ρ、**u**）计算 |
| `src/lbm/solver.cpp` | LBM | BGK/MRT 碰撞 + 周期性流式迁移 + 内置 BC 调用 + 宏观量二次更新（v0.1.1 修复）|
| `src/lbm/boundary.cpp` | LBM | 面专用反弹边界（South/North/West/East）、四面 Zou-He 速度边界条件（v0.1.1 修复）|
| `src/ibm/marker.cpp` | IBM | 拉格朗日标记点集创建（圆形截面、柔性丝状体） |
| `src/ibm/interpolation.cpp` | IBM | δ 函数速度插值（欧拉→拉格朗日）与力展布（拉格朗日→欧拉） |
| `src/fsi/structure.cpp` | FSI | Euler-Bernoulli 梁有限元（Newmark-β 时间积分） |
| `src/fsi/coupling.cpp` | FSI | 分区显式 FSI 耦合：插值→直接力→展布→结构推进→速度同步 |
| `src/capi/lbm_capi.cpp` | C ABI | `lbm_grid_*` / `lbm_solver_*` C 函数（供 Rust FFI 调用） |
| `src/plugins/plugin_registry.cpp` | 插件 | C 函数指针→C++ 虚函数适配器 + 全局单例注册中心 |

### 4.2 声明静态库目标

```cmake
add_library(lbm_core STATIC ${CORE_SOURCES})
```

- `STATIC`：生成静态库（`.a` / `.lib`），链接到 Rust 时不产生运行时动态库依赖
- 库名 `lbm_core` 对应产物 `liblbm_core.a`（Unix）/ `lbm_core.lib`（Windows）

### 4.3 头文件搜索路径

```cmake
target_include_directories(lbm_core
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>
)
```

- `PUBLIC`：该路径对 `lbm_core` 自身**及**所有链接它的目标均可见
- `$<BUILD_INTERFACE:…>`：仅在当前构建树有效（源码内构建）
- `$<INSTALL_INTERFACE:…>`：仅在 `cmake --install` 后的安装树有效

`CMAKE_CURRENT_SOURCE_DIR` 是 CMake 自动变量，指向当前处理的 `CMakeLists.txt` 所在目录，即 `core/`。因此头文件路径为 `core/include/`。

> **为什么用 `BUILD_INTERFACE` 生成器表达式？**  
> 若直接写绝对路径，安装后的库会携带构建机器的路径，导致其他机器无法使用。使用生成器表达式可以为构建和安装两种场景提供不同路径。

### 4.4 MPI 链接与预处理宏

```cmake
if(ENABLE_MPI)
    target_link_libraries(lbm_core PUBLIC MPI::MPI_CXX)
    target_compile_definitions(lbm_core PUBLIC LBM_ENABLE_MPI)
endif()
```

- `target_link_libraries(… PUBLIC MPI::MPI_CXX)`：链接 MPI 导入目标，并将其**传播**给链接 `lbm_core` 的所有目标
- `target_compile_definitions(… PUBLIC LBM_ENABLE_MPI)`：定义预处理宏 `LBM_ENABLE_MPI`，使 `core/src/` 中的 `#ifdef LBM_ENABLE_MPI` 分支生效

### 4.5 OpenMP 链接与预处理宏

```cmake
if(ENABLE_OPENMP)
    target_link_libraries(lbm_core PUBLIC OpenMP::OpenMP_CXX)
    target_compile_definitions(lbm_core PUBLIC LBM_ENABLE_OPENMP)
endif()
```

与 MPI 逻辑相同。`OpenMP::OpenMP_CXX` 目标携带 `-fopenmp` 标志，使 `#pragma omp parallel for` 等指令在编译时生效。

### 4.6 库文件输出路径

```cmake
set_target_properties(lbm_core PROPERTIES
    ARCHIVE_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/lib"
)
```

`CMAKE_BINARY_DIR` 是顶层构建目录（`cmake -B <build_dir>` 的 `<build_dir>`）。  
将 `liblbm_core.a` 统一放到 `<build_dir>/lib/`，与 `build.rs` 中的 `cargo:rustc-link-search=native=<dst>/lib` 对应。

### 4.7 安装规则

```cmake
install(TARGETS lbm_core ARCHIVE DESTINATION lib)
install(DIRECTORY include/ DESTINATION include)
```

执行 `cmake --install` 时：
- 将 `liblbm_core.a` 安装到 `<prefix>/lib/`
- 将 `core/include/` 下所有头文件安装到 `<prefix>/include/`

这使得非 Cargo 构建环境（纯 C++ 项目）也能复用本库。

文件位置：`core/tests/CMakeLists.txt`

本文件职责：将 4 个测试源文件编译为可执行程序 `test_lbm`，并注册为 CTest 测试用例。

### 5.1 测试可执行文件

```cmake
add_executable(test_lbm
    test_runner.cpp
    test_lbm.cpp

```

4 个源文件的分工：

| 文件 | 职责 |
|------|------|

| `test_lbm.cpp` | LBM 求解器测试：质量守恒（∑ρ 不变）、`f_eq` 归一化（∑f_eq = ρ）、方腔流物理正确性（中线速度/南壁无滑移/腔体环流/有限性，v0.1.1 新增）、反弹 BC 幽灵方向精准赋值（v0.1.1 新增）|

### 5.2 链接核心库

```cmake
target_link_libraries(test_lbm PRIVATE lbm_core)
```

- `PRIVATE`：`lbm_core` 的依赖仅对 `test_lbm` 本身有效，不向外传播
- 链接 `lbm_core` 后，其 `PUBLIC` 头文件路径（`core/include/`）自动对 `test_lbm` 可见


## 6 cargo build 与独立 cmake 的行为差异对比

| 构建方式 | `ENABLE_MPI` | `ENABLE_OPENMP` | `BUILD_TESTS` | `CMAKE_BUILD_TYPE` |
|---------|-------------|----------------|--------------|-------------------|
| `cmake -S . -B build`（直接） | `ON`（默认） | `ON`（默认） | `ON`（默认） | 未设置（由生成器决定） |
| `cargo build` | `OFF`（build.rs 覆盖） | `OFF`（build.rs 覆盖） | `OFF`（build.rs 固定） | `Debug` 或 `Release` |
| `LBM_ENABLE_MPI=ON cargo build` | `ON`（环境变量覆盖） | `OFF` | `OFF` | `Debug` 或 `Release` |
| `cargo build --release` | `OFF` | `OFF` | `OFF` | `Release` |

**关键差异总结：**
1. `cargo build` 默认关闭 MPI/OpenMP，避免 CI 环境中缺少依赖导致编译失败；
2. `cmake` 直接构建默认开启 MPI/OpenMP，假设开发机已安装相关库；
3. `BUILD_TESTS` 通过 `cargo build` 时**强制为 `OFF`**，不可通过环境变量覆盖；
4. `cmake` 直接构建时不设置 `CMAKE_BUILD_TYPE`，由生成器自行决定（例如 Visual Studio 默认 Debug）。

## 7 常见构建错误与解决方案

### 7.1 LNK1181：找不到 `stdc++.lib`（Windows）

**错误信息**：
```
error: linking with `link.exe` failed: exit code: 1181
LINK1181: cannot open input file 'stdc++.lib'
```

**根因**：`build.rs` 对 Windows 也打印了 `cargo:rustc-link-lib=stdc++`，而 MSVC 工具链没有 `stdc++.lib`。

**修复**（已在本项目 `build.rs` 中实现）：

```rust
match target_os.as_str() {
    "macos" | "ios" => println!("cargo:rustc-link-lib=c++"),
    "windows"       => {} // MSVC 自动链接，无需声明
    _               => println!("cargo:rustc-link-lib=stdc++"),
}
```

**验证**：`cargo build` 在 Windows 上不再报此错误；Linux/macOS 不受影响。

### 7.2 LNK1120 / LNK2001：运行时库冲突（Windows Debug 构建）

**错误信息**：
```
LNK2001: unresolved external symbol __calloc_dbg
LNK1120: 1 unresolved externals
```

**根因**：cmake Debug 配置默认用 `/MDd`，Rust 始终用 `/MD`，两者引用了不同的 CRT 符号集。

**修复**（已在本项目 `CMakeLists.txt` 中实现）：

```cmake
if(MSVC)
    set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreadedDLL")  # 强制所有配置用 /MD
endif()
```

**验证**：`cargo build`（Debug）和 `cargo build --release`（Release）在 Windows 上均成功。

### 7.3 `lbm_grid_new returned null`（运行时 panic）

**错误信息**（Rust 侧）：
```
thread 'main' panicked at 'lbm_grid_new returned null'
```

**可能原因**：
1. 传入的 `model_id` 超出 0–2 范围（C++ 侧参数校验失败）；
2. 系统内存不足（`new (std::nothrow)` 返回 `nullptr`）；
3. `cmake` 未成功编译（`liblbm_core.a` 为空或损坏）。

**诊断步骤**：
```bash
# 检查 cmake 是否成功生成库
ls -la target/*/build/lbm-bindings-*/out/lib/liblbm_core.a

# 检查传入参数
# 在 orchestrator/main.rs 中打印 nx/ny/nz 和 model
```

### 7.4 增量构建不触发（修改 C++ 后 cargo build 没有重新编译）

**可能原因**：`cargo:rerun-if-changed` 路径相对于 `build.rs` 所在目录，而非项目根目录。

**验证方法**：
```bash
# 强制重新运行 build.rs
touch bindings/build.rs
cargo build
```

若强制后能正常重新编译，说明路径配置正确，是 Cargo 缓存未正确检测到文件变化（罕见）。

## 8 增量构建机制详解

### 8.1 Cargo 缓存机制

首次 `cargo build` 成功后，Cargo 在 `target/` 目录中记录：

1. `cargo:rerun-if-changed` 指定的所有文件的**内容哈希**；
2. `cargo:rerun-if-env-changed` 指定的所有环境变量的**值**；
3. `build.rs` 本身的内容哈希；
4. `Cargo.toml` 和依赖版本信息。

### 8.2 二次构建决策流程

```
cargo build（第二次）
    │
    ├─ build.rs 内容变化？
    │       YES → 重新运行 build.rs → 重新 cmake → 重新链接
    │       NO  → 继续检查
    │
    ├─ core/src/ 或 core/include/ 有文件变化？
    │       YES → 重新运行 build.rs → cmake 增量编译（只编译变化文件）→ 重新链接
    │       NO  → 继续检查
    │
    ├─ LBM_ENABLE_MPI / LBM_ENABLE_OPENMP 环境变量变化？
    │       YES → 重新运行 build.rs → cmake 全量重新配置 → 重新编译 → 重新链接
    │       NO  → 继续检查
    │
    └─ 只有 Rust 源文件变化？
            → 跳过 build.rs，直接编译 Rust，链接已缓存的 liblbm_core.a（最快）
```

### 8.3 典型场景耗时对比

| 场景 | 是否重新运行 build.rs | cmake 行为 | 预计耗时 |
|------|---------------------|-----------|---------|
| 只修改 `orchestrator/src/main.rs` | ❌ 否 | 不触发 | ~2s（只编译 Rust） |
| 修改 `core/src/lbm/solver.cpp` | ✅ 是 | 增量编译（只编 solver.cpp） | ~10-20s |
| 修改 `core/include/lbm/lattice.hpp` | ✅ 是 | 增量编译（所有包含该头文件的 .cpp） | ~20-60s |
| `LBM_ENABLE_MPI=ON cargo build`（首次） | ✅ 是 | 全量重新配置 + 编译 | ~60-120s |
| 首次 `cargo build` | ✅ 是 | 全量编译 | ~60-180s |
